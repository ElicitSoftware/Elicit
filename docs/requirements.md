# Elicit Platform — Requirements Catalog (Umbrella)

Source: [`docs/vision.md`](vision.md), the Survey, Admin and FHHS `application.properties`,
`docker-compose.yml`, `DeploymentScript.md`, the `elicitsoftware/elicit_db` image's
init scripts, [`docs/BRAND_SYSTEM_IMPLEMENTATION_GUIDE.md`](BRAND_SYSTEM_IMPLEMENTATION_GUIDE.md),
[`docs/I18N_IMPLEMENTATION_GUIDE.md`](I18N_IMPLEMENTATION_GUIDE.md), and the module
use cases this manual provisions for (Admin UC-005, UC-025, UC-027, UC-028; Survey UC-004,
UC-005, UC-007; FHHS UC-001..UC-005; Author UC-048).

This catalog covers the **umbrella repository only** — the platform as one
deployable whole. Each module keeps its own catalog for its own behavior; module
requirement IDs are unrelated to the IDs here.

Roles referenced below:

- **Deployment Operator** — the primary actor; installs and configures an Elicit
  site. Comfortable with PostgreSQL, a container runtime, and an
  OIDC provider; has not seen Elicit before.
- **Release Engineer** — builds and stamps the manual as part of a release.
- **Report Developer** — writes a report service of the site's own: a small web
  application that Survey and Admin call with a respondent's id and that answers with
  the report. Reads the custom reports chapter; may be the deployment operator.
- **Survey Administrator** / **Survey Author** — secondary actors; they take over
  where this manual stops, through their own manuals.

| C-018 | The Compose Stacks Are for Development and Evaluation | `docker-compose.yml`, the multi-site suites' compose files and the services bundled with them (database, Keycloak and its realm, mail catcher, SFTP server, trace collector) exist for development, evaluation and the end-to-end suites. They are not a production installation and hold no real respondent data; a real site is installed against its own database, identity provider and network (FR-013) and secured (FR-043). The manual must say so wherever it describes the stack. `docker-compose.yml` serves evaluation and development alike and runs from a directory holding nothing but itself: it mounts no file (the brand and translation mounts are in it, commented out), keeps its data in named volumes and pulls every image at one platform version, the database (`elicitsoftware/elicit_db`) and the identity provider with the realm built in (`elicitsoftware/elicit_keycloak`) included, which defaults to the release the file comes with, never to `latest`; a developer runs local builds with `ELICIT_TAG=latest`. | Technical  | High     | Open   |
| C-019 | Module-to-Module Calls Are Authenticated | Every call one platform module makes to another — between Survey, Admin, FHHS, Pedigree, Author and Author's preview Survey — carries `Authorization: Bearer` with the deployment's service token (`ELICIT_SERVICE_TOKEN`, `elicit.service.token`), one value of at least 32 characters per deployment. A receiver checks it on every path it serves for other modules (Survey: `/api` except `/api/pdf/download`; FHHS: everything outside `/q`; Pedigree: everything but `/healthz`) and answers `401` to a missing or wrong token. A module with no token starts, reports not ready through a health check named `service-token`, answers `503` on those paths and makes no service call. A caller sends the token only to an origin the deployment's configuration names: the address of a module it is configured with, or an entry of `elicit.service.trusted-origins`; an address that arrives in a definition file never receives it for that reason alone. Health endpoints stay open. No image carries a token: the compose stacks supply a documented development value (C-018), which a module warns about at startup, and `check-properties.sh` fails when a module's shipped configuration gives the token a value. | Technical  | High     | Open   |
| C-020 | No Prescribed Role Is a Superuser | No database role Elicit prescribes holds the superuser attribute. The schema owner (`elicit_owner`) owns the `survey` and `surveyreport` schemas and what the migrations create in them, and through its membership of `dbowner` holds `CREATE` on the Elicit database, which is what each survey's reporting schema (`report_<slug>`) needs; it can do nothing else in the cluster. The role script in the manual (FR-008) and the `elicitsoftware/elicit_db` image create the roles that way, the compose stacks run that image at a named version, and `resetDatabase.sh V2` narrows the roles of the V2 test copy with the statements `DeploymentScript.md` gives a site whose cluster an earlier script prepared, so the greenfield and the brownfield run of `fullTest.sh` both exercise a schema owner that is not a superuser. The bundled image's own administrative account (`POSTGRES_USER`) is a superuser of the bundled cluster, belongs to the evaluation stack (C-018) and is no role a module connects as. | Technical  | High     | Open   |

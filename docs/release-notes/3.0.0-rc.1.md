# Elicit 3.0.0 Release Candidate 1 — Release Notes

**Status:** in preparation. This file collects what changes between 3.0.0-beta.1 and
3.0.0-rc.1 as the work merges; it is complete only once the release is tagged. So far it covers
the hardening work. Everything in the [3.0.0-beta.1 notes](3.0.0-beta.1.md) still applies.

**Release date:** _to be set when tagged_
**Supersedes:** 3.0.0-beta.1

---

## Breaking changes

Read these before upgrading from 3.0.0-beta.1.

### The service token

- **Every module needs `ELICIT_SERVICE_TOKEN`.** Survey, Admin, FHHS, Pedigree and Author
  identify themselves to each other with one secret, the same value on every module of a
  deployment. Generate it once and supply it like the database passwords:

  ```sh
  openssl rand -hex 32
  ```

  The Java modules also read it as `elicit.service.token`; Pedigree reads the environment
  variable only.
- **Without it a module is not ready.** Survey, Admin, FHHS and Author start, log a warning,
  and report not ready on `/q/health/ready` with the reason. Pedigree's `/healthz` stays up and
  its `/svg` answers 503. A value shorter than 32 characters stops the module at startup.
- **Trusted origins.** A module sends the token only to an origin the deployment names in
  `ELICIT_SERVICE_TRUSTED_ORIGINS` (`elicit.service.trusted-origins`, comma-separated, each a
  scheme, host and optional port with no path or trailing slash), and to the addresses its own
  configuration already names (`elicit.survey.url`, `pedigree.url`). A site running the Family
  History reports lists the origin its survey definition's report addresses use, on Survey,
  Admin and FHHS.
- **What answers whom.** Survey's `/api` paths other than `/api/pdf/download`, every FHHS path
  outside `/q`, and every Pedigree path other than `/healthz` answer `401` to a caller without
  the token. A script or monitor that called one of them directly must send
  `Authorization: Bearer <token>` or use the health endpoints.
- **The compose stack carries a development default**, so `docker compose up -d` needs no
  setup. A real site supplies its own value; a module running with the development default says
  so in its log, and Admin lists it as setup work.

The installation manual's chapter "The service token" has the full description, including
rotation.

### The database roles

- **No role Elicit prescribes is a superuser.** The schema owner (`elicit_owner`) and the owner
  group (`dbowner`) are created without the attribute by the installation manual's role script
  and by `elicitsoftware/elicit_db:3.0.0-rc.1`, and `elicit_owner` is now a member of
  `dbowner`.
- **A cluster that already exists is not changed by upgrading.** Roles are created once. Run the
  three statements in `DeploymentScript.md`, "Upgrading to a schema owner that is not a
  superuser", to narrow them; the modules run either way.
- **The compose files name `elicitsoftware/elicit_db:3.0.0-rc.1`** instead of `latest`.

### FHHS

- **`GET /familyhistory/health` is removed.** Use `/q/health/ready`.
- **The diagnostic endpoints under `/familyhistory/debug` are removed.**

### Admin

- **The subject edit link is `/register/<subject id>`.** The `?accessCode=` form introduced in
  3.0.0-beta.1 no longer loads a subject.
- **Registration is scoped by department.** The Register page, the CSV import and the
  integration API (`/api/secured/add/...`) accept a subject only for a department the caller is
  assigned to, when the caller has a console user record.
- **The OIDC diagnostics page shows raw tokens in development mode only**, whatever
  `elicit.debug.reveal-tokens` says.

### Survey

- **The access log changed shape.** It records method, path and protocol without the query
  string, no `Referer`, and nothing for `/login/<access code>`. A log parser written for the
  beta's pattern needs updating.
- **`/login/<access code>` leaves the address bar at `/login`** after filling the field.

## Security

- **Module-to-module calls are authenticated** with the service token (above).
- **The schema owner is not a superuser** (above). The role every module migrates as owns the
  Elicit schemas and can create a schema in the Elicit database, and nothing else in the
  cluster.
- **Response headers.** Survey, Admin and Author send `Strict-Transport-Security`,
  `X-Content-Type-Options`, a `Referrer-Policy` and a frame-ancestors policy themselves, with
  no proxy configuration needed.
- **Outbound addresses.** Survey accepts only `http` and `https` addresses for reports and the
  post-survey hand-off.
- **Report output is encoded.** FHHS encodes every value it writes into report HTML and
  validates report requests.
- **Admin's message template preview** renders in an isolated frame.
- **Author** limits upload sizes and serves an SVG brand image so that it cannot run script
  when opened directly.
- **Pedigree** releases its graphics device and temporary file after every drawing.
- **Installation manual.** A new chapter, "Securing the site", describes each control a site
  puts in place and closes with a checklist. The Compose chapter now presents the stack as
  development and evaluation only.

## Upgrading from 3.0.0-beta.1

1. Generate a service token and set `ELICIT_SERVICE_TOKEN` on every module.
2. On a site running the Family History reports, set `ELICIT_SERVICE_TRUSTED_ORIGINS` on
   Survey, Admin and FHHS to the origin the report addresses use.
3. On a cluster prepared before this release, narrow the schema owner and the owner group with
   the three statements in `DeploymentScript.md`.
4. Upgrade all modules together and restart them together.
5. Check that each module is ready (`/q/health/ready`, and `/healthz` on Pedigree), then apply
   a definition and open a report.

No change to a schema or to data is needed for anything in this file; step 3 changes two roles.

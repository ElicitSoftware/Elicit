# Elicit 3.0.0 Release Candidate 1 — Release Notes

**Status:** release candidate. It is the first 3.0.0 pre-release with release notes:
3.0.0-beta.1 was published as images only, and what was written for it is part of this file.
Upgrading from 3.0.0-beta.1 is not supported. A site that ran it installs this release on a new
database or restores its 2.x backup and upgrades from there.

**Release date:** _to be set when tagged_
**Supersedes:** 2.2.0
**Modules in this release:** Survey, Admin, FHHS, Pedigree and Author, each at 3.0.0-rc.1, and
this umbrella repository (compose file, scripts, installation manual).
**Images:** `elicitsoftware/survey`, `admin`, `fhhs`, `pedigree` and `author`, each tagged
`3.0.0-rc.1`, and the database image `elicitsoftware/elicit_db:3.0.0-rc.1`. A pre-release is
published under its exact version only, so `latest` still points at 2.2.0 until 3.0.0 ships.
The compose file pulls the application images at the tag in `ELICIT_TAG` and names the database
image's version itself:

```sh
ELICIT_TAG=3.0.0-rc.1 docker compose up -d
```

or put `ELICIT_TAG=3.0.0-rc.1` in a `.env` file beside it.

This is a **release candidate**. It is feature-complete for 3.0.0. Run it in a test environment
before production. It has not been through a production rollout yet.

Survey, Admin and FHHS share one database and **must be upgraded together from this
release**. A 3.0.0 module against a 2.x database, or the other way round, will not start.
Take a database backup before upgrading: no module ships a down-migration, so the backup is the
only way back.

## Highlights

- **Versioned survey definitions (Kimball Type 2).** Every structural survey table (steps,
  sections, questions, relationships and others) now keeps its history as effective-dated rows
  with durable keys. Respondents' answers stay tied to the version of the survey they actually
  saw, and a revised definition can be applied over an existing survey (Admin UC-017).
- **One reporting schema per survey.** Each survey gets its own star schema, named
  `report_<survey name>` (for the Family History Survey, `report_family_history_survey`) and
  recorded on `survey.surveys.report_schema`. It is built when the survey definition is applied,
  with no restart needed, and can be renamed from the Admin console.
- **Multilingual.** The Survey, Admin and Author interfaces can be offered in any language a site
  mounts. ElicitSoftware ships a curated set beside the release: Latin American Spanish (`es-419`)
  and Arabic (`ar`, right to left), in `elicit-i18n/`. The images themselves carry English only.
  Survey content can be translated too: the translations travel in the `.elicit` file and are
  shown in the respondent's language.
- **Access codes.** The respondent's credential is now called an *access code* everywhere:
  database, configuration, API, email templates and branding. This is a breaking rename; see
  [Breaking changes](#breaking-changes).
- **Admin console additions:** a Participation page, a System section, the administrator's
  manual, export of a survey definition, and department assignment.
- **Security hardening:** the modules authenticate their calls to each other with a service
  token, no database role Elicit prescribes is a superuser, outbound TLS is verified, outbound
  calls have timeouts, SFTP host keys are checked, SVG rendering no longer fetches external
  resources, and database passwords are no longer built in. See [Security](#security).

## Breaking changes

Read these before upgrading. The step-by-step procedures are in `DeploymentScript.md`.

### The service token

- **Every module needs `ELICIT_SERVICE_TOKEN`.** Survey, Admin, FHHS, Pedigree and Author
  identify themselves to each other with one secret, the same value on every module of a
  deployment. Generate it once and supply it like the database passwords:

  ```sh
  openssl rand -hex 32
  ```

  The Java modules also read it as `elicit.service.token`; Pedigree reads the environment
  variable only.
- **Without it a module is not ready.** Survey, Admin, FHHS and Author start, log a warning,
  and report not ready on `/q/health/ready` with the reason. Pedigree's `/healthz` stays up and
  its `/svg` answers 503. A value shorter than 32 characters stops the module at startup.
- **Trusted origins.** A module sends the token only to an origin the deployment names in
  `ELICIT_SERVICE_TRUSTED_ORIGINS` (`elicit.service.trusted-origins`, comma-separated, each a
  scheme, host and optional port with no path or trailing slash), and to the addresses its own
  configuration already names (`elicit.survey.url`, `pedigree.url`). A site running the Family
  History reports lists the origin its survey definition's report addresses use, on Survey,
  Admin and FHHS.
- **What answers whom.** Survey's `/api` paths other than `/api/pdf/download`, every FHHS path
  outside `/q`, and every Pedigree path other than `/healthz` answer `401` to a caller without
  the token. A script or monitor that called one of them directly must send
  `Authorization: Bearer <token>` or use the health endpoints.
- **The compose stack carries a development default**, so `docker compose up -d` needs no
  setup. A real site supplies its own value; a module running with the development default says
  so in its log, and Admin lists it as setup work.

The installation manual's chapter "The service token" has the full description, including
rotation.

### The database roles

- **No role Elicit prescribes is a superuser.** The schema owner (`elicit_owner`) and the owner
  group (`dbowner`) are created without the attribute by the installation manual's role script
  and by `elicitsoftware/elicit_db:3.0.0-rc.1`, and `elicit_owner` is now a member of
  `dbowner`.
- **A cluster that already exists is not changed by upgrading.** Roles are created once. Run the
  three statements in `DeploymentScript.md`, "Upgrading to a schema owner that is not a
  superuser", to narrow them; the modules run either way.
- **The compose files name `elicitsoftware/elicit_db:3.0.0-rc.1`** instead of `latest`.

### Database and deployment

- **Upgrade Survey, Admin and FHHS together.** Survey has to finish its migrations before
  Admin and FHHS start. Docker Compose handles this through `depends_on` and health checks; a
  deployment without Compose must start Survey first and wait for it to be ready. FHHS starts
  after Admin.
- **The old reporting schema is dropped and rebuilt.** Survey's V021 drops the reporting tables
  in `surveyreport`, leaving only `dim_date` and `dim_status`, and rebuilds each survey's star
  from `survey.answers` in its own schema. What changes for report consumers:
  - **Schema name.** Queries and BI connections that read `surveyreport.fact_sections_view`
    must read `<report_schema>.fact_sections_view` instead.
  - **Ids.** `fact_sections.id` and every `dim_*.id` get new values. Extracts keyed on them
    must be pulled again.
  - **Corrected columns.** `fact_sections.step_key` and `section_key` now hold dimension ids
    rather than display orders.
  - **No reporting tables in between.** The drop and the rebuild are not one transaction, so
    upgrade outside reporting hours.
- **Database passwords are required.** Survey and FHHS no longer have built-in passwords. Set
  `ELICIT_DB_PASSWORD` and `ELICIT_OWNER_DB_PASSWORD` (or
  `quarkus.datasource.password` and `quarkus.datasource.owner.password`). Without them a
  module logs `no password was provided`, retries for about 8 minutes, then exits.
- **No seeded survey or department on a new install.** The Family History Survey arrives by
  importing `FHHS/family-history-survey.elicit` in Admin's Apply Survey Definition. An
  administrator's first sign-in on a new database asks them to create a department first
  (Admin UC-028). Existing databases keep their "Testing Department".

### Access codes (formerly "token")

- **Database:** `survey.respondents.token` is now `access_code`. The `survey.status` view's
  column is renamed to match.
- **Configuration:** `token.autoRegister` is now `accessCode.autoRegister`. The old key is
  ignored.
- **Email templates:** `<TOKEN>` is now `<ACCESS_CODE>`. Stored templates are converted
  automatically.
- **FHHS SFTP XML template:** `{Token}` is now `{AccessCode}`. This template comes from
  deployment configuration, so change it by hand.
- **Integration API:** `/api/secured/add/subject`, `/add/subjects` and `/add/csv` return
  `status.accessCode` instead of `status.token`.
- **Admin links:** the subject edit link is `/register/<subject id>`. The `?token=` form no
  longer loads a subject, and the access code is not part of the address.
- **Branding:** `.elicit-token` is now `.elicit-access-code`, and `--brand-token-bg` and
  `--brand-token-text` are now `--brand-access-code-bg` and `--brand-access-code-text`.
- **Respondent sessions:** respondents who are mid-survey during the upgrade must sign in again.
  Their answers are kept.

### FHHS

- **SFTP delivery is off by default.** Set `family.history.sftp.enabled=true` to keep sending
  reports to the SFTP destination. Without it, reports silently stop being delivered.
- **The SFTP server's host key is verified.** Set `family.history.sftp.knownHosts` to either
  `known_hosts` lines (from `ssh-keyscan -p <port> <host>`) or the path of a known_hosts file.
  If it is unset, the connection is refused. `family.history.sftp.strictHostKeyChecking=false`
  turns the check off; use that only for local development.
- **FHHS no longer installs the Family History Survey.** Import it in Admin > Apply Survey
  Definition from `FHHS/family-history-survey.elicit`. Until the import is applied:
  - FHHS still starts, but `/q/health/ready` reports it as not ready.
  - Every report request gets HTTP 503, with a message saying the survey must be imported.

  No restart is needed afterwards: FHHS becomes ready on its next health check.
- **`GET /familyhistory/health` is removed.** Use `/q/health/ready`.
- **The diagnostic endpoints under `/familyhistory/debug` are removed.**
- **The SFTP metadata file is XML-escaped.** Every value placed into
  `family.history.sftp.xml.template` is escaped, and characters XML 1.0 forbids are left out. A
  receiving system that parsed the file as XML reads the values as recorded; one that matched
  the raw text, for example `&` in a name, sees `&amp;` instead.

### Admin

- **Registration is scoped by department.** The Register page, the CSV import and the
  integration API (`/api/secured/add/...`) accept a subject only for a department the caller is
  assigned to: a user through their console user record, a machine client through its import
  client record.
- **The registration API is for import clients only.** `/api/secured/add/subject`,
  `/add/subjects` and `/add/csv` accept the `elicit_importer` role and no other. A token for a
  user, an administrator included, is answered 403; people register subjects on the Register
  page, whose CSV upload is unchanged.
- **A machine client needs an import client record.** Create it under Admin > Import Clients
  with the name the client's tokens carry (for a Keycloak service account,
  `service-account-<client id>`) and the departments it registers into. Without an active
  record, or with `elicit_user` or `elicit_admin` on the same token, every request is answered
  403.
- **No user holds `elicit_importer`.** `elicit_admin` and `elicit_user` no longer imply it,
  the Users screen no longer offers it, and the upgrade removes it from `survey.user_roles`.
- **For an existing subject the API answers with the outcome only**: the external ID and the
  department, and no access code. The access code is returned for a subject the call created.
- **An excluded subject's outcome is spelled `Excluded Subject`.** The API returned
  `Exluded Subject` before; a caller that compares `importStatus` against it must change. The
  other two outcomes, `New Subject` and `Existing Subject`, are unchanged.
- **The OIDC diagnostics page shows raw tokens in development mode only**, whatever
  `elicit.debug.reveal-tokens` says.
- **`/api/secured/test` and `/api/secured/roles` are removed.** The OIDC diagnostics page shows
  what the roles endpoint did.
- **Respondent export and import are scoped by department.** An administrator exports only a
  respondent whose subjects are all in their departments (any other answers 404, as for a
  missing id), and imports only into their own departments (any other is reported as an
  unknown department code).

### Survey

- **The access log changed shape.** It records method, path and protocol without the query
  string, no `Referer`, and nothing for `/login/<access code>`. A log parser written for the
  earlier pattern needs updating.
- **`/login/<access code>` leaves the address bar at `/login`** after filling the field.
- **Authored HTML is cleaned before a respondent sees it.** HTML and MODAL question text and a
  survey's description keep their formatting but lose scripts, event handlers, `javascript:`
  links, frames and forms, and a survey's title is shown as plain text. A definition that relied
  on any of these renders without them; the definition itself is unchanged.

### Forwarding headers

- **Survey, Admin and Author honor forwarding headers only from a trusted proxy.** Each reads
  `Forwarded` and `X-Forwarded-*` only from the addresses in `ELICIT_TRUSTED_PROXIES`
  (`quarkus.http.proxy.trusted-proxies`), by default loopback and the private ranges. A reverse
  proxy or load balancer on a public address must be listed there, or Admin and Author build
  their sign-in redirects with their own address and every application logs the proxy as the
  client. Narrow it to the proxy's address on a real site.
- **Survey's startup diagnostics name `quarkus.http.proxy.trusted-proxies`.** They previously
  advised `quarkus.http.proxy.trusted-proxy`, which Quarkus does not read; a site that set that
  key should set `ELICIT_TRUSTED_PROXIES` instead.

### Outbound connections

- **TLS certificates are verified.** `quarkus.tls.trust-all` is no longer set. If a report
  service, post-survey action or identity provider uses a private CA, add it with
  `quarkus.tls.trust-store.pem.certs`.
- **Admin needs Survey's address.** Admin calls Survey to build reporting schemas and to print
  the built-in respondent summary. Set `elicit.survey.url`; the default `http://survey:8080` only
  resolves inside Docker Compose. Survey's `/api` paths (other than `/api/pdf/download`) are meant
  for Admin only: do not expose them publicly. For the GKE campsites, see the
  `survey_campsite` and `admin_campsite` merge requests.

## New features

### Survey

- **Versioned survey structure.** Kimball Type 2 SCD with durable, portable keys. Structure is
  resolved as of the respondent's first access (UC-002).
- **Per-survey reporting.** A per-survey reporting star schema, built on demand through
  `POST /api/etl/build?survey=<key>` and renamed through
  `POST /api/etl/schema/<key>/rename?name=` (UC-008). `dim_date` now runs through 2050, and its
  weekend flag is fixed.
- **Interface languages from a mount.** The image carries English only. Survey reads every other
  language from `translations_<tag>.properties` in `<i18n.file.system.path>/survey/`. A mounted file
  may hold only the texts it changes; the rest fall back to English. The settings:
  - `i18n.offered.locales` offers fewer languages than are mounted.
  - `i18n-config.json` at the mount root sets a language's text direction and size.
  - `i18n.direction.<tag>` and `i18n.font-scale.<tag>` override the direction and size for one
    deployment.

  With nothing mounted, Survey offers English only and shows no language selector (UC-007).
- **Translated survey content.** Survey content is shown in the respondent's language, wherever
  the survey publishes a translation and the site offers the language (UC-009). The date picker's
  calendar follows the language.
- **Repeats.** A question or section can repeat once for each item selected.
- **Built-in respondent report.** A respondent report rendered in process and over HTTP (UC-014).
  Report marks (`survey.report_items`) choose what it shows (UC-013).
- **Progress stamps.** Respondent progress is recorded in `answers.presented_dt`,
  `respondents.last_activity_dt`, and `answers.saved_dt`, which is now set only when the
  respondent changes a value (UC-012).
- **Reports page skipped** when a survey lists no reports.
- **ETL switch.** `elicit.etl.enabled=false` turns the reporting ETL off on preview instances.
- **Startup diagnostics** are logged when the service starts.
- **Auto-registration is a site choice.** `accessCode.autoRegister=true` lets anyone start a survey
  with an access code of their own, for a survey open to the public. The login page no longer
  shows a test-only warning and the startup report no longer warns about it (UC-001 BR-002,
  Admin#96).

### Admin

- **Import Clients page (UC-032).** The machine clients of the registration API have a page of
  their own beside Users: name, description, active flag and departments, with create, edit,
  deactivate and delete. A name is a user or an import client, never both.
- **Participation page (UC-031).** It shows:
  - live counts and the questions marked for reporting;
  - charts, drop-off, stalled respondents and time per step;
  - small-cell suppression;
  - CSV and PDF export.

  Two settings tune it: `elicit.participation.small-cell` (default 5) and
  `elicit.participation.stalled-days` (default 14).
- **System section.** Shows the running version, both database connections, each module's
  migrations, brand resolution and mail settings, with a test email button. It also checks that
  every outbound dependency can be reached, and its OIDC page shows the current sign-in's roles.
- **Survey definitions.**
  - Update Survey Definition applies a revised `.elicit` over an existing survey, including
    retirements and content translations (UC-017).
  - Export Survey Definition writes a survey back out as a `.elicit` file.
  - When a definition file is refused, the console shows why.
  - Applying a definition rebuilds that survey's reporting schema.
- **Reporting schema rename** from the console.
- **Portable exports.** Respondent export and import work across deployments and carry the
  progress stamps.
- **Departments.** A department assignment is required (UC-028).
- **Registration.** RegisterView lets the administrator choose which survey a new subject is
  registered on.
- **Administrator's manual** inside the application (UC-029).
- **Auto-registered respondents.** A respondent Survey auto-registered has no subject, and the
  console used to hide it. Search Subjects now lists it, to every console account, with
  "Auto-registered" where the department would be, and Participation counts it under a row of
  its own (UC-002 BR-181, UC-031 BR-120, Admin#96; migration `V0.0.27`).
- **Fixes:**
  - Search Subjects shows every row of the page.
  - Access code generation no longer retries forever.
  - A fresh database with no survey can start and accept a definition.

### FHHS

- **Survey by import.** FHHS takes the Family History Survey by import and refuses service until
  it arrives (UC-005). It reads the survey's own reporting schema, whatever it is named.
- **Verified SFTP delivery** (NFR-007, UC-004 BR-006).
- **Survey definition fixes:**
  - Every placeholder is delimited.
  - `{S1}` on the Mother and Father steps is filled from an answer.
  - The defaultless placeholders get an empty default.

### Pedigree

- No change to the drawing. The service now requires the service token, runs in its container
  as an unprivileged user, and refuses a request body over 1 MB with `413`.
- CI builds the image and smoke-tests `/healthz`, `/svg` and the service token.

### Platform (this repository)

- **Installation manual** (`docs/manual/`, a PDF). It is built with the images and checked
  against the modules' configuration properties, so a drifted reference fails the build.
- **Curated translations** in `elicit-i18n/`: Spanish and Arabic for Survey and Admin, plus
  `i18n-config.json`. Docker Compose mounts it at `/opt/i18n`.
- `buildDockerImages.sh` builds all modules and the manual in parallel. Before building, it checks
  that the images carry English only and that `elicit-i18n/` gives Survey and Admin the same
  languages.
- `status.sh` probes each service's health endpoint and says why one is not ready.
- `resetDatabase.sh V2|V3` resets the local database for brownfield or greenfield test runs.
- The local Docker Compose stack starts FHHS after Admin, so their first migrations do not
  collide.
- The Compose stack includes Author, the authoring tool, with its respondent preview, and is
  presented throughout as a stack for development and evaluation, not for a production site.

## The default brand

The brand every application shows when a site mounts none of its own is new.

- **Logo.** The Choice E mark, three answer rows stacked into an E with the middle one
  selected, replaces the clipboard and checkmark in the header, the browser tab, the Branding
  pages and the manuals.
- **Color.** The primary color is the mark's navy, `#0A3D62` (was `#1B629C`). The accent,
  Verdigris `#22775D`, and the neutrals are unchanged.
- **Typeface.** IBM Plex Sans and IBM Plex Mono, with IBM Plex Sans Arabic for Arabic. The font
  files are part of the brand and each application serves them itself, so a page requests no
  font from a third party.
- **A brand can carry its own fonts.** A relative `url()` in a brand stylesheet now resolves
  against the brand: `url("fonts/Face.woff2")` in `typography/brand-typography.css` is the
  brand's `typography/fonts/Face.woff2`. See "External branding" in the installation manual.
- **One source.** `elicit-brand/` in the umbrella repository is the default brand, and the copy
  inside each image is the same files; `checkBrand.sh` fails a build where they differ.

A site that mounts its own brand sees no change. A site whose brand began as a copy of the
default keeps the old look until it copies the new files; a site that mounts only some files
(colors, say) gets the new default for the rest, as with any partial brand.

## Security

- **Module-to-module calls are authenticated** with the service token (see
  [Breaking changes](#breaking-changes)).
- **The schema owner is not a superuser.** The role every module migrates as owns the Elicit
  schemas and can create a schema in the Elicit database, and nothing else in the cluster.
- **TLS trust-all removed** from Survey and Admin. Outbound HTTPS now verifies certificates.
- **Timeouts on outbound calls.** Survey's post-survey actions and report services, and FHHS's
  calls to the reports of a delivery, get a 5-second connect timeout and a 60-second answer
  timeout. A service that never answers can no longer hold a respondent's request or a delivery
  forever.
- **Outbound addresses.** Survey accepts only `http` and `https` addresses for reports and the
  post-survey hand-off.
- **SVG rendering hardened.** Apache Batik is upgraded from 1.16 to 1.20 (CVE-2022-44729 and
  CVE-2022-44730), and PDF rendering now refuses external resources and scripts in SVG.
- **SFTP.** FHHS moves from the unmaintained `com.jcraft:jsch:0.1.55` to
  `com.github.mwiede:jsch:2.28.8` and verifies the server's host key.
- **No default database passwords** in Survey or FHHS.
- **Response headers.** Survey, Admin and Author send `Strict-Transport-Security`,
  `X-Content-Type-Options`, a `Referrer-Policy` and a frame-ancestors policy themselves, with
  no proxy configuration needed.
- **Report output is encoded.** FHHS encodes every value it writes into report HTML and
  validates report requests.
- **Admin's message template preview** renders in an isolated frame.
- **Author** limits upload sizes and serves an SVG brand image so that it cannot run script
  when opened directly.
- **Pedigree** runs as an unprivileged user, limits the size of a request, and releases its
  graphics device and temporary file after every drawing.
- **Security advisories.** Eight issues found in the release review are fixed and published:

  | Advisory | Module | Issue |
  |---|---|---|
  | [GHSA-mmfj-j88x-fmp2](https://github.com/ElicitSoftware/Admin/security/advisories/GHSA-mmfj-j88x-fmp2) | Admin | Forwarding headers trusted from any client; debugging endpoints exposed |

  | [GHSA-94w2-7qhh-cv4c](https://github.com/ElicitSoftware/Survey/security/advisories/GHSA-94w2-7qhh-cv4c) | Survey | Report service HTML inserted into the respondent page unsanitized |

  | [GHSA-72mm-cc8q-g47j](https://github.com/ElicitSoftware/Author/security/advisories/GHSA-72mm-cc8q-g47j) | Author | Stored XSS through HTML question text in the designer preview |

  Survey passes report content, the text of HTML and MODAL questions and a survey's
  description through an allowlist before it reaches the page, and shows a survey's title as
  plain text; Author does the same for its question previews. Content made only of text,
  tables, lists, links and SVG drawings, the Family History Survey and its reports included,
  renders unchanged.
- **Installation manual.** A chapter, "Securing the site", describes each control a site puts
  in place and closes with a checklist.

- Java 25, Quarkus 3.40.1.2 LTS (was 3.39.2), and Vaadin 25.3.5 (was 25.2.7).

## Upgrading from 2.x

1. **Back up the database.** There is no rollback other than restoring it.
2. **Change the configuration** listed under [Breaking changes](#breaking-changes):
   - the service token: generate one and set `ELICIT_SERVICE_TOKEN` on every module, and on a
     site running the Family History reports set `ELICIT_SERVICE_TRUSTED_ORIGINS` on Survey,
     Admin and FHHS to the origin the report addresses use;
   - database passwords;
   - `accessCode.autoRegister`;
   - the FHHS SFTP settings and `{AccessCode}`;
   - `elicit.survey.url` for Admin;
   - `ELICIT_TRUSTED_PROXIES` for Survey, Admin and Author, when the reverse proxy is not on a
     private address;
   - any private CA trust store;
   - any custom brand CSS;
   - the translations mount, if the site offers languages other than English: mount
     `elicit-i18n/` and set `i18n.file.system.path` for Survey and Admin.
3. **Narrow the database roles.** On a cluster prepared before this release, run the three
   statements in `DeploymentScript.md`, "Upgrading to a schema owner that is not a superuser".
   The modules run either way.
4. **Upgrade all modules together.** Start Survey and wait until it is ready, then start Admin,
   then FHHS.
5. **Check that each module is ready** (`/q/health/ready`, and `/healthz` on Pedigree).
6. **Verify the reporting schemas.**
   `select name, report_schema from survey.surveys;` should name a schema for every survey, and
   `report_family_history_survey.dim_step` should have 15 rows for the Family History Survey.
   Then open a report.
7. **Tell report consumers** about the new schema name and the new reporting ids.

If the database also moves to a host with a different glibc, PostgreSQL warns about a
collation version mismatch. Fix it with `REINDEX DATABASE` and
`ALTER DATABASE … REFRESH COLLATION VERSION` before starting the applications (see
`DeploymentScript.md`).

## New installation

Follow the installation manual (`docs/manual/elicit-installation-manual.pdf`). Then, in order:

1. Generate a service token and start the modules with it.
2. Sign in as an administrator and create a department.
3. Apply `FHHS/family-history-survey.elicit` in Admin > Apply Survey Definition.

## Known issues and limitations

- **Temporary upgrade code.** The V2-to-V3 upgrade path (`ManualSchemaMigrator` and
  `db/migration-v3/` in Survey and FHHS) is temporary. It will be removed in a later release,
  once every deployment has upgraded.
- **FHHS applies its V0.0.9 migration on its second start** after a brownfield upgrade. It
  needs no action, and the first start is healthy.
- **Prometheus is not part of the local Compose stack.** Jaeger collects traces only.

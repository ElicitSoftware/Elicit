# Elicit 3.0.0 Release Candidate 2 — Release Notes

**Status:** release candidate. These notes list what changed since 3.0.0-rc.1; everything in
the [3.0.0-rc.1 notes](3.0.0-rc.1.md) still applies.

**Release date:** 2026-11-20
**Supersedes:** 3.0.0-rc.1
**Modules in this release:** Survey, Admin, FHHS, Pedigree and Author, each at 3.0.0-rc.2, and
this umbrella repository.
**Images:** `elicitsoftware/survey`, `admin`, `fhhs`, `pedigree` and `author`, each tagged
`3.0.0-rc.2`. The database image is unchanged at `elicitsoftware/elicit_db:3.0.0-rc.1`.

```sh
ELICIT_TAG=3.0.0-rc.2 docker compose up -d
```

As before, Survey, Admin and FHHS share one database and are upgraded together. Take a database
backup first: Admin's V0.0.28 drops a column, and no module ships a down-migration.

---

## Changed behavior

### Admin

- **Department notification addresses are discarded.** Migration V0.0.28 drops
  `survey.departments.notification_emails` (Admin#221). Nothing in Elicit ever read the column,
  sent mail to it or showed it, so no behavior is lost, but any addresses a site entered by hand
  are deleted. Copy them out before upgrading if they are wanted:

  ```sql
  select id, name, notification_emails from survey.departments
   where notification_emails is not null;
  ```

- **A registration record that breaks a subject rule is refused before anything is created**
  (Admin#220, UC-010 BR-188). The integration API (`/api/secured/add/subject`, `/add/subjects`,
  `/add/csv`) and the Register page's CSV upload check each record against the Register page's
  own rules first: a first and last name, a valid email address, a phone, when given, as
  `###-###-####`, a date of birth in the past, and no field longer than it is stored (50
  characters for a name, 255 for the email address). A record that fails is refused naming each
  field at fault, and creates no subject, respondent, access code or message. Before, a malformed
  phone or an over-long field failed only when the subject was saved: the single endpoint
  answered with an unhandled error, a batch reported an unexpected error, and in a CSV import it
  could fail the upload. A caller that sent phones in another format must reformat them or leave
  the phone out; a blank phone column is no phone and is accepted.

### Survey

- **Clearing an answer stores the question as unanswered** (Survey#230, UC-002 BR-017), for
  every question type. An emptied text, email, password or multi-select field is stored as no
  answer (`answers.text_value` null) instead of an empty string; an emptied number is no longer
  stored as the text `null`; and clearing a date, date-time, time or number no longer fails.
  Branching rules that read the question are recalculated as for an unanswered question, and a
  cleared repeat count counts as zero, so the repeated questions or sections are removed. The
  review page and the reports no longer show the old answer. A report query that treated an
  empty string as "cleared" should test for null.
- **Date and date-time bounds are checked on the server, as whole days** (Survey#226, UC-002
  BR-016). A bounded date or date-time answer is checked again before the section is left,
  whether or not the question is required. A `DATE_TIME_PICKER` question's minimum and maximum
  are now read as days since 1970-01-01, like a `DATE_PICKER` question's, accepting any time from
  the start of the minimum day to the end of the maximum day. Before, they were read as HHMM times
  on the day the question was answered; a definition that set times on a date-time question must
  set days instead (a time bound belongs on a `TIME_PICKER` question). An answer outside its
  bounds shows the question's own validation text, or else a message naming the earliest or latest
  allowed date in the respondent's language, translated in the curated Spanish and Arabic.

## Fixes

- **`Notice.txt` lists jsoup** in the Survey and Author images (Survey#232, Author#161). The
  3.0.0-rc.1 images left out this MIT-licensed dependency.
- **Pedigree's `/healthz` reports the image's version** (Pedigree#22). The release workflow now
  passes it to the build; the 3.0.0-rc.1 image reports `dev`.

## Documentation

- **Author's installation manual documents `ELICIT_TRUSTED_PROXIES`** (Author#159). It said
  Author trusted forwarding headers from any client, as before 3.0.0-rc.1.
- **Every repository has a security policy** (`SECURITY.md`, Elicit#180), linked from the issue
  forms: report a vulnerability privately, not in a public issue.

## Upgrading from 3.0.0-rc.1

1. **Back up the database**, and copy out any department notification addresses (see above).
2. **Upgrade all modules together** at `3.0.0-rc.2`: start Survey and wait until it is ready,
   then Admin, then FHHS. Admin applies V0.0.28 on its first start.
3. **Check that each module is ready** (`/q/health/ready`, and `/healthz` on Pedigree, which
   should now report `3.0.0-rc.2`).
4. **Tell integration clients** about the subject rules above, and **authors** about date-time
   bounds.

No configuration changes. Upgrading from 2.x follows the
[3.0.0-rc.1 notes](3.0.0-rc.1.md#upgrading-from-2x), with these changes applied on the way.
